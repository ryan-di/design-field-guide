# Before you ship, ask these

Design Field Guide v35 (2026-11) · Part 1 · Good design
Live: https://ryan-di.github.io/design-field-guide/#ch-good-checklist
Cite as: Design Field Guide v35, #ch-good-checklist

> Evidence boundary: this is a learning guide. Its demos and product examples are illustrations written for the book, not verified product documentation, so check a product’s own docs before citing how it behaves. Tools named in it are 2026 examples, not endorsements.

A review checklist built from this part. Tick through it on your next change. Each question links to the entry that explains it. Ticks here reset when you leave the page.

**The problem**

- [ ] Can I state the problem without naming a solution? [Frame the problem](https://ryan-di.github.io/design-field-guide/#good-problem-framing)
- [ ] Do we know how we’ll tell it worked? [Define “good” before building](https://ryan-di.github.io/design-field-guide/#good-success-criteria)
- [ ] Does it work reliably before it tries to delight? [Hierarchy of needs](https://ryan-di.github.io/design-field-guide/#good-needs-hierarchy)

**Clarity**

- [ ] Blur it: does the most important thing still stand out? [Visual hierarchy](https://ryan-di.github.io/design-field-guide/#good-visual-hierarchy)
- [ ] Are related things grouped by space, with more space between groups? [Proximity](https://ryan-di.github.io/design-field-guide/#good-proximity)
- [ ] Do spacing and edges follow the scale and the grid? [Spacing rhythm](https://ryan-di.github.io/design-field-guide/#good-spacing-rhythm)
- [ ] Does text meet 4.5:1, and is no meaning carried by color alone? [Contrast, and never color alone](https://ryan-di.github.io/design-field-guide/#good-contrast)

**Consistency**

- [ ] Same thing, same look, same name, same place? [Internal and external consistency](https://ryan-di.github.io/design-field-guide/#good-consistency)
- [ ] Is it built from tokens and shared components, not one-off values? [Design tokens](https://ryan-di.github.io/design-field-guide/#good-design-tokens)
- [ ] Is every exception deliberate, with a reason? [Break it on purpose](https://ryan-di.github.io/design-field-guide/#good-break-on-purpose)

**Words**

- [ ] Does every button say what happens when you press it? [Labels that say what happens](https://ryan-di.github.io/design-field-guide/#good-labels)
- [ ] Does every error say what to do next? [Error messages that help](https://ryan-di.github.io/design-field-guide/#good-error-copy)
- [ ] Would a newcomer understand every word? [Plain words, one term per concept](https://ryan-di.github.io/design-field-guide/#good-plain-language)

**Craft**

- [ ] Have all states been designed: loading, empty, error, disabled? [Interaction states](https://ryan-di.github.io/design-field-guide/#interaction-states)
- [ ] Did I try long, missing and huge data? [Design with real, messy data](https://ryan-di.github.io/design-field-guide/#good-edge-cases)
- [ ] Is motion quick, purposeful, and off when reduced motion is on? [Motion with a purpose](https://ryan-di.github.io/design-field-guide/#good-motion)
- [ ] Can I do the whole task with the keyboard, and always see focus? [Keyboard paths are craft](https://ryan-di.github.io/design-field-guide/#good-keyboard-focus)

**Judgment**

- [ ] Has someone critiqued it against the goal? [Critique against the goal](https://ryan-di.github.io/design-field-guide/#good-critique)
- [ ] Did I do a quick heuristic pass? [Heuristic review](https://ryan-di.github.io/design-field-guide/#good-heuristic-review)
- [ ] Is the reasoning written down where others will find it? [Write down the reasoning](https://ryan-di.github.io/design-field-guide/#good-design-rationale)
