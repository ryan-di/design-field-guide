A/B test
A test where each group of people gets a different version, so you can compare what they do. It’s judged on one main number agreed before the test, plus a guardrail. Measure against the brief
Artifact
Something small a stage of the work leaves for others to read or try, such as a brief, a decision or a plan. In Part 4 it is often an artifact page: one shared web page an agent made. Follow one problem through
Attention, lifetime and control
The three things every component promises: how much it interrupts, how long it stays, and what people can do with it. Read every component as a promise
Axis
One dimension with two ends that options vary along, such as how loud a message is, from silent to blocking. Two axes make a grid, and each cell is a direction. Vary along named axes
Bet
The guess about what people need that a direction is built around, such as “never interrupt” or “make it fixable in one step”. Get many directions cheaply
Brief
A short note written before anyone builds: who has the problem, what should change, what’s off limits and how you’ll know it worked. Write the problem brief
Context pack
What a new teammate would need on their first day: design tokens, components to reuse, copy rules, examples of good screens, repo conventions and the design frames. Pack the context
Critique
Judging work against what it is for: start from the goal, say what serves it and what doesn’t, then suggest a fix. It comes in three kinds: direction for early sketches, flow once the steps exist as rough screens, and polish when the screens are close to done. Critique against the goal
Decision matrix
A table that scores each direction from 1 to 5 against each criterion in the brief. Each criterion has a weight, so what the problem is about counts more. Score directions against the brief
Definition of done
The list of checks a change must pass before you call it finished. Each is something you could see or run, and says who checks it. Define done so both of you can check it
Design rationale
The reasoning behind a design decision, written down: the problem, the options you considered, the one you chose and why. Write down the reasoning
Design token
A shared value with a name, such as a corner radius, a spacing step, a color or a text size. Design tokens
Diff
The lines a change adds and removes, as a pull request shows them. Skim it for new strings, styles and components. Call out what people will see
Direction
One clearly different answer to the brief, explored on its own, so you can lay several side by side and choose. Get many directions cheaply
End-to-end spec
A test that uses the app the way people do, through its screens, such as a Playwright spec. Unit tests check the logic underneath. Let agents prove their work
Feature flag
A switch that keeps new code turned off for people, so a step can merge before the step that completes it lands. Plan, then take small steps
Fidelity
How close a sketch, mock or prototype is to the real thing, from a sketch to a branch in the app. Each level shows some things and hides others. See what each fidelity can show
Guardrail
One number that must not get worse, with a limit you set before looking. Measure against the brief
Heuristic review
A check of a design against a short list of rules of thumb, such as Jakob Nielsen’s ten usability heuristics. It finds likely problems, not proven ones. Heuristic review
Interruption ladder
The ways to tell people something, from quietest to loudest: inline message, badge, toast, banner, dialog. Use the lowest step that still does the job. Read every component as a promise
Loop
The stages every change goes through: Problem, Brief, Explore, Decide, Build, Check and Learn. What Learn finds starts the next round. The loop
MCP
A standard way to plug tools into an agent, such as a connector that lets it read Figma frames. Pack the context
Pattern
A solution shape that has worked many times before, such as undo instead of a confirm. Every pattern has a trade-off. Name the problem before the fix
Plan mode
A way of working where the agent proposes a plan and changes nothing until you agree to it, such as Claude Code’s plan mode. Plan, then take small steps
Problem frame
Who has the problem, what they’re trying to do and what stops them, written down before anyone draws a screen. Frame the problem
Severity
How bad a usability problem is, from 0 to 4: 0 isn’t a problem after all, 1 is cosmetic, 2 minor, 3 major, where people struggle or lose work, and 4 a catastrophe, where they can’t finish the task. See the severity scale
Subagent
A helper agent that works alongside the others, such as one for each direction. Get many directions cheaply
Success criteria
What you would see or count if a change worked. Define “good” before building
Trade-off
What a pattern costs. Hidden things get forgotten, for example, and experts pay an extra click. Name the problem before the fix
Usability test
Watching real people use a design to do a task, and noting where they stall. It finds problems that a review can only guess at. Watch a few people use it
UX call
A choice people will see in a change, such as the wording, the spacing or which kind of dialog appears. Decide each one and name it in the pull request. Call out what people will see
Weight
How much a criterion counts in a decision matrix. Score directions against the brief
Worktree
A separate working copy of the code, made with git, so several agents can work at once without clashing. Get many directions cheaply
