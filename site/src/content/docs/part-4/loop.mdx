Good work runs in a loop: frame the problem, explore options, decide, build, check, and learn for the next round. Agents can do much of the exploring and building, but the framing, deciding and checking stay yours.

<article class="entry essay" id="eff-loop" data-entry data-name="The loop">

<div class="entry-head">

## The loop \{#eff-loop-h\}

<Learned id="eff-loop" />

</div>

Every change goes through the same loop. Problem and Brief frame the work, then come Explore, Decide, Build and Check, and what Learn finds starts the next round. Each stage takes something in and hands something on, so a skipped stage leaves the next one guessing.

Agents make Build fast, so the stages around it matter more: framing the problem before, and checking the result after.

<Raw html={F0} />

Each stage at a glance. [What you own, what agents do](#eff-ownership) shows how the split moves with the kind of work.

<Raw html={F1} />

### Rules \{#eff-loop-rules\}

Five rules keep the loop useful.

<div class="cs essay-cs">

<section class="rule" id="eff-loop-rule-1">

#### 1. Frame the problem before you build \{#eff-loop-rule-1-h\}

A ticket that names a fix sends the agent straight to Build, and it builds that fix quickly and well. If the fix doesn’t solve the real problem, people still have it and the fast build was wasted. [Frame the problem](/part-1/problem/#good-problem-framing) and write a short brief first, so the agent explores answers to the right question.

<Raw html={F2} />

</section>

<section class="rule" id="eff-loop-rule-2">

#### 2. Close the loop \{#eff-loop-rule-2-h\}

A merged pull request means the change shipped, not that it worked. When shipping is the last step, nobody checks, and the problems it didn’t solve come back weeks later as support requests. Check the change against the brief and write down what you learned, because that note becomes the problem for the next round.

<Raw html={F3} />

</section>

<section class="rule" id="eff-loop-rule-3">

#### 3. Choose yourself, and write down why \{#eff-loop-rule-3-h\}

Agents are quick to build the first idea that fits. If you merge it because it’s already built, the agent made the choice, and later nobody can say why it was done this way. Ask for several options, pick one yourself, and write the reason in the ticket or the PR.

<Raw html={F4} />

</section>

<section class="rule" id="eff-loop-rule-4">

#### 4. Try it in the real app \{#eff-loop-rule-4-h\}

Tests an agent wrote check what the agent thought of, so they can all pass while the change fails people in a case nobody listed. Open the change in the real app and walk through the brief yourself. A problem found before the merge costs minutes, not a bug report.

<Raw html={F5} />

</section>

<section class="rule" id="eff-loop-rule-5">

#### 5. Frame a hunch as a question \{#eff-loop-rule-5-h\}

Some work starts from a hunch, with no evidence yet and a goal that’s still moving. Written as a spec, the hunch gets built as if it were known, and a whole round passes before anyone learns it was wrong. Write the brief as a question instead: what you want to find out, what you believe now and what would change your mind. Keep the rounds short, and let each Learn rewrite the brief.

<Raw html={F6} />

</section>

## What you own, what agents do \{#eff-ownership-h\}

<Learned id="eff-ownership" />

</div>

Agents are good at wide, repeatable work: searching a codebase, writing test scaffolds, making many variations. You keep the judgment: framing the problem, choosing between options and checking the result. Between agent steps, put a checkpoint where you read what came back before the next step starts.

Where [the loop](#eff-loop) names the stages of a change, this entry says who owns each one. Agent output often sounds sure, but confident wording isn’t evidence, so ask for the file, the test or the screenshot behind each claim before you build on it.

<Raw html={F9} />

<p id="eff-ownership-draft">An agent can draft any part of a brief, and any option or check, as long as it says where each part came from, such as a support thread, a ticket or a file. Confirming who has the problem, the evidence and the problem itself stays with you, and so do the choice between options and every judgment call. The table shows the split from the demo for each kind of work.</p>

<Raw html={F10} />

### Rules \{#eff-ownership-rules\}

Four rules keep the split between you and agents useful.

<div class="cs essay-cs">

<section class="rule" id="eff-ownership-rule-1">

#### 1. Ask for trade-offs, not a verdict \{#eff-ownership-rule-1-h\}

When you ask an agent to pick the best design, it picks one and sounds sure about it, so you get a choice with nothing to check and can’t explain it later. Ask for the options and what each one is good at and costs, then make the choice yourself. If you already lean one way, write it down first, so the agent’s confident answer doesn’t become yours, as [Hear their read first](/part-1/critique/#good-critique-rule-4) explains.

<Raw html={F11} />

</section>

<section class="rule" id="eff-ownership-rule-2">

#### 2. Hand over the wide, repetitive work \{#eff-ownership-rule-2-h\}

Some tasks are long only because there is a lot of the same thing: every use of a color token, every form to update, ten variations of a layout. Doing them by hand takes hours that framing and checking needed. Agents can do that work, several at once, and you spend the time you get back reading what they found.

<Raw html={F12} />

</section>

<section class="rule" id="eff-ownership-rule-3">

#### 3. Stop after each agent step \{#eff-ownership-rule-3-h\}

If exploring flows straight into planning and building, an early misreading carries all the way through, and you find out at the end, when many files have changed. Stop after each step and read what came back. Claude Code’s plan mode, where the agent proposes a plan and changes no files until you approve it, is one built-in checkpoint.

<Raw html={F13} />

</section>

<section class="rule" id="eff-ownership-rule-4">

#### 4. Review the plan before the build \{#eff-ownership-rule-4-h\}

A wrong approach takes a minute to fix in a short plan, but in a finished diff (the changed lines of code) it runs through many files, and fixing it means building again. Read the plan before the agent builds, as [Plan, then take small steps](/part-4/build/#eff-small-steps) explains.

<Raw html={F14} />

</section>
